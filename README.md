# TETHER

TETHER is being built as a modular-monolith hospital management system for private hospital deployments. The interface follows the supplied desktop-style references: grouped left navigation, contextual actions, compact status indicators, and data-dense searchable tables. Use only synthetic records in the local development database.

## Architecture baseline

- **Frontend:** React + TypeScript + Ant Design.
- **Backend:** Python 3.13 + FastAPI.
- **Supported development and production datastore:** PostgreSQL 16+. It will be the authoritative store for patient, clinical, and financial records. The current local setup remains on SQLite until the PostgreSQL development service and migrations are established.
- **Live updates:** WebSockets/SignalR-style events will be added behind authenticated APIs when a workflow needs them.
- **Caching:** Redis is intentionally not part of the first slice; introduce it only for measured caching or coordination needs.
- **Structure:** Modular monolith, with capability boundaries for identity, patient access, clinical care, inpatient, billing, inventory, workforce, and reporting.

The current development slice includes session-based login, server-side permission checks, login lockout, TOTP MFA for privileged accounts, SuperAdmin RBAC administration, patient registration and OPD queueing, nurse triage, doctor consultation notes, and permission-scoped operation events. A global refresh/status control polls every two seconds while the app is visible, backs off after failures, and refreshes open lists without replacing unsaved form text. Patient and draft-note updates use optimistic versions to reject stale saves. Patient numbers are generated by the system; next-of-kin contact and relationship details can be recorded at registration. The SQLite development database is active. PostgreSQL 16+ is the supported database target, with SQLAlchemy's `asyncpg` driver declared as a required dependency; its migrations have not yet been applied or verified against a live server. Other operational modules, comprehensive audit coverage, identity-provider integration, and production hardening are not complete. Do not use real patient, staff, or payment data or expose this development system to a network.

## Run the frontend

```powershell
cd frontend
npm.cmd install
npm.cmd run dev
```

Patient registration, the OPD queue, nursing triage, doctor consultation workflows, and shared change synchronization are connected to the backend and SQLite development database. Other navigation modules are not yet operational.

## Run the backend

Python 3.12 or newer is required. From the repository root:

```powershell
Set-Location backend
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[dev]"
.\.venv\Scripts\python.exe -m uvicorn app.main:app --reload
```

`GET /api/v1/health/live` confirms the process is running; `/api/v1/health/ready` checks the configured database. The local `.env` uses SQLite for development; set `HMS_DATABASE_URL` to change it. Authentication uses a random opaque, server-side session cookie (stored as a hash), a readable CSRF cookie/header pair, Argon2id password hashes, and TOTP MFA for privileged accounts. No default credentials or production secrets are provided.

## Database

`backend/migrations/001_core.sql` through `007_system_change_events.sql` define the identity, RBAC overrides, patient, OPD, audit, system-owner, MFA, clinical-workflow, and operation-event schemas. They are PostgreSQL SQL migrations; a PostgreSQL connection URL must use the async driver format `postgresql+asyncpg://<user>:<password>@<host>:5432/<database>`. The migrations have not been applied or tested against a running PostgreSQL server in this workspace.

The current local development database remains SQLite. `HMS_DATABASE_URL` is set in `backend/.env`; run `.\.venv\Scripts\python.exe -m app.bootstrap_roles` from `backend` to create/update the SQLite tables and seed the role catalog. A database with exactly one active SuperAdmin claims that account as owner; if multiple active SuperAdmins already exist, set `HMS_SYSTEM_OWNER_USERNAME` to the intended account for the one-time claim. On a new installation, run `.\.venv\Scripts\python.exe -m app.bootstrap_admin` after seeding to create the first administrator interactively; that account is the system owner.

Privileged MFA is required for the system owner, SuperAdmins, and accounts with effective `identity.users.manage` or `identity.roles.manage` permissions. Password login starts enrollment for a privileged account without MFA; protected APIs remain blocked until the authenticator code is verified. Once enabled, the 6-digit TOTP code is required at login. TOTP seeds are encrypted using `HMS_MFA_ENCRYPTION_KEY`. Generate a key once from `backend` with `.\.venv\Scripts\python.exe -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"` and store it in the untracked `backend/.env` and an approved secrets store. Do not lose or change this key without a recovery plan: existing TOTP seeds cannot be decrypted with a different key.

In **Administration & audit**, a SuperAdmin can reset another account's MFA; this revokes its active sessions and requires re-enrollment. The system owner cannot be reset through the web UI. The trusted-host `.\.venv\Scripts\python.exe -m app.bootstrap_admin --recover-owner` flow resets the owner's authenticator and requires enrollment again. Recovery codes are not implemented.

For a repeatable SQLite migration push, run:

```powershell
cd backend
.\.venv\Scripts\python.exe -m app.migrate_sqlite
.\.venv\Scripts\python.exe -m app.bootstrap_roles
```

The migration command creates missing SQLAlchemy tables and additive columns, records applied SQLite migration versions in `schema_migrations`, creates the system-owner unique partial index, and adds append-only SQLite triggers for audit and operation-event updates/deletes. It is safe to rerun.

Do not switch the existing local database URL to PostgreSQL until the local PostgreSQL service and versioned migrations are configured and verified. No SQLite-to-PostgreSQL data migration is performed automatically. Authentication and patient-access APIs are versioned under `/api/v1`.

### Local PostgreSQL service

Docker Compose provides a local PostgreSQL 16 service, bound to loopback only, with a persistent named volume and a readiness health check. Add or update `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, and `POSTGRES_PORT` in the existing untracked `backend/.env`; set a unique local password and leave `HMS_DATABASE_URL` on SQLite for now. The variable names and non-secret defaults are shown in `backend/.env.example`.

From the repository root, start and inspect the service with:

```powershell
docker compose --env-file backend/.env up -d postgres
docker compose --env-file backend/.env ps
```

Stop it without deleting its data with:

```powershell
docker compose --env-file backend/.env stop postgres
```

The database files remain in the `tether_postgres_data` volume. Do not remove that volume unless you intend to permanently delete the local PostgreSQL data. This service does not migrate or connect the existing SQLite database; PostgreSQL schema setup remains for the migration task.

## User, role, and permission administration

The supplied HMS roles-and-permissions workbook is represented in `backend/app/core/rbac.py`. The seeded catalog contains 33 roles and 410 permissions, including seven action keys per matrix function. Ordinary roles receive only actions defined in their role matrix. `SuperAdmin` and the designated system owner bypass backend permission checks, including for permissions added later. The built-in SuperAdmin role itself is immutable. The unique database owner cannot be deactivated, lose SuperAdmin status, or have account/access settings changed by another administrator. Owner-specific permission overrides are rejected because owner access cannot be narrowed. A SuperAdmin may assign the role to another user. The built-in `System Administrator` can manage user accounts and assign approved non-SuperAdmin roles, but cannot change role or permission policy. Users can hold multiple roles. SuperAdmin-managed individual allow/deny overrides apply after role grants: explicit deny wins over inherited grants, and explicit allow adds access.

For the current SQLite development database, seed or refresh the catalog from `backend` with:

```powershell
.\.venv\Scripts\python.exe -m app.bootstrap_roles
```

Sign in at the frontend and open **Administration & audit** to manage users, assign roles, edit departments, reset passwords, change custom roles and permissions, configure role privileges, set individual permission overrides, or review the audit log. The owner row is marked and cannot be deactivated, demoted, or modified by another account. To recover the owner after a login lockout or lost password, run `.\.venv\Scripts\python.exe -m app.bootstrap_admin --recover-owner` from `backend` on a trusted host; this prompts for a new password, restores the owner role/status, clears lockout, revokes sessions, and writes an audit event. Initial and reset passwords must be at least 14 characters and should be shared through an approved secure channel. Admin password resets also clear lockouts and revoke active sessions. Account deactivation also revokes active sessions.

The Internal Auditor and System Administrator roles can read the audit log; attempts to read it are themselves recorded. Audit events cover authentication, identity/role changes, patient searches and reads, patient registration/updates, OPD visit creation, triage, consultation-note changes/signing, and visit completion; clinical note bodies and triage values are not copied into audit metadata. A separate append-only operation-event stream powers the live refresh indicator and contains only category/action/time and internal resource references. Its API filters events by module permissions and omits patient identifiers, note contents, payment amounts, and actor details. New mutating audit actions under the supported patient, clinical, admissions, laboratory, pharmacy, billing, messaging, and identity prefixes automatically create operation events; use those action prefixes in future modules. Cash collection and refund approval privileges cannot be combined on one role or user. The optional Dietician, Physiotherapist, and Mortuary Officer roles from the supplemental guidance are not seeded because their access scope was not specified.

The patient-access slice stores basic demographics and optional next-of-kin details, generates an opaque TETHER patient number, supports search/update, flags likely duplicate registrations for manual review, and opens a linked OPD visit. Nurses can record a single structured triage entry; doctors can create editable drafts, sign and lock notes, add signed-note addenda, and complete a visit. These fields, validation ranges, state transitions, and duplicate rules are development defaults, not hospital-approved policy. There is no patient merge/history, appointment scheduling, diagnosis/coding, diagnostics, inpatient, billing, insurance, pharmacy, theatre, procurement, HR, or operational reporting workflow yet. Permission entries for those modules do not mean the modules are implemented. The supplied workbook and supplemental guidance are planning material, not legal, clinical, or regulatory approval. Do not use real records or payments; confirm data fields, access policy, retention, privacy, and clinical governance before any real-data pilot. PostgreSQL migration and deployment remain deferred.

## Development sequence

1. Foundation: identity, permission enforcement, audit pipeline, and application shell (development implementation present; production hardening remains).
2. Patient registration, next-of-kin details, duplicate review, and persisted OPD queue (SQLite-backed slice present; appointments and patient merge/history remain).
3. Nursing triage and doctor consultation note workflow (initial SQLite-backed slice present; diagnoses, diagnostics, orders, results, clinical approval, and hospital governance remain).
4. Billing, payments, receipts, corrections, approvals, and reconciliation.
5. Admissions, wards, bed allocation, transfers, and discharge.
6. Pharmacy, inventory, procurement, and stock audit.
7. Accounting, workforce, insurance, and reporting.
8. External integrations, security testing, recovery drills, and deployment hardening.

Before any real deployment, complete threat modeling, applicable Kenyan legal/privacy review, role and permission design, encrypted backup/restore drills, infrastructure hardening, and independent security testing.
